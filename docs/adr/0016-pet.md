# ADR 0016: Pet (animal atendido)

- **Status:** Proposed (revisado após o parecer do ChatGPT no PR 45; aguarda nova revisão dele e a aprovação do Matheus antes de qualquer código)
- **Data:** 16/11/2026
- **Esforço:** ALTO (muda o domínio, o banco e a integridade dos agendamentos)
- **Contexto de produto:** o nicho aprovado é banho e tosa (marca **Pelo & Ponto**). O atendimento é prestado ao **animal**, não só ao tutor; a agenda e a fila precisam mostrar quem é o pet.

## Decisão proposta

### 1. Modelo e restrições no banco
Tabela `pets`: `id`, `customer_id` (tutor, obrigatório), `name`, `species`, `breed`, `size`, `notes`, `active`, `created_at`, `updated_at`.

| Campo | Regra |
|---|---|
| `name` | obrigatório, 1 a 80 caracteres **depois** de normalizar |
| `species` | **obrigatório**: `DOG` ou `CAT` |
| `breed` | opcional, 1 a 80 caracteres depois de normalizar (vazio vira nulo) |
| `size` | opcional: `SMALL`, `MEDIUM`, `LARGE` |
| `notes` | opcional, 1 a 500 caracteres depois de normalizar (vazio vira nulo), escrito pelo tutor |
| `active` | arquivar sem apagar; não há exclusão física |

- **Normalização** (na aplicação, antes de gravar): remover espaços nas pontas; em `name` e `breed`, colapsar espaços internos em um só; em `notes`, quebras de linha `\r\n` viram `\n` e caracteres de controle (exceto `\n`) são recusados. Texto só de espaços equivale a vazio: `name` vazio é 400; `breed` e `notes` vazios viram nulo.
- **As mesmas regras valem no PostgreSQL** (restrições `CHECK`), para que nenhum caminho alternativo grave dado inválido: `species IN ('DOG','CAT')`; `size IS NULL OR size IN (...)`; `char_length(name) BETWEEN 1 AND 80 AND name = btrim(name)`; `breed IS NULL OR (char_length(breed) BETWEEN 1 AND 80 AND breed = btrim(breed))`; `notes IS NULL OR (char_length(notes) BETWEEN 1 AND 500 AND notes = btrim(notes))`. Testes inserem direto por SQL e esperam a violação.
- **Fora de escopo:** peso, vacinas, fotos, alergias estruturadas, prontuário, histórico clínico.

### 2. Vínculo com o agendamento e snapshot
`appointments.pet_id` **nullable** (preserva os agendamentos existentes), com **chave estrangeira composta `(pet_id, customer_id)` → `pets (id, customer_id)`**: o banco impede um agendamento de usar o pet de outro cliente, mesmo se a aplicação errar.

**Snapshot (decisão: adotar, como recomendou o ChatGPT).** O agendamento guarda uma cópia dos dados do pet no momento da reserva: `pet_name`, `pet_species`, `pet_breed`, `pet_size`, `pet_notes` (todas nulas quando `pet_id` é nulo; `CHECK` garante que `pet_id` nulo ⇔ `pet_name` nulo, e repete as restrições de formato do item 1). **Agenda, fila e "Meus agendamentos" leem somente o snapshot**, nunca fazem junção com `pets`: o que o prestador vê vem do agendamento que ele opera, sem consultar o cadastro do tutor.
- O cadastro do pet continua sendo a fonte **atual**; o histórico (concluído e cancelado) é congelado.
- **Divergência consciente, para o ChatGPT atacar:** a recomendação dele é que alterar o cadastro nunca reescreva snapshots. Proponho uma exceção estreita: **enquanto o agendamento está `SCHEDULED`** (ainda não chegou), editar o pet **atualiza** o snapshot dele. Motivo: o tutor que marca o banho na segunda e na quarta avisa "ficou com coceira na pata" precisa que o prestador veja isso na sexta; congelar na reserva esconderia o dado mais útil justo para quem ainda vai atender. A partir de `CHECKED_IN`, `COMPLETED` ou `CANCELLED` o snapshot **nunca mais muda**, então o histórico fica fiel. Se o ChatGPT preferir o snapshot puro, a exceção sai sem afetar o resto (basta remover um `UPDATE`); o custo seria o aviso na tela de que alterar o pet não muda reservas futuras.
- Atualização do snapshot na edição: na mesma transação que altera o pet, `UPDATE appointments SET pet_* = ..., version = version + 1 WHERE pet_id = :id AND status = 'SCHEDULED'`. O `version + 1` é obrigatório: `appointments` usa bloqueio otimista (`version`) e o JPA grava todas as colunas; sem incrementar, um check-in carregado antes da edição gravaria o snapshot velho por cima do novo. Com o incremento, o bloqueio otimista recusa esse check-in em vez de sobrescrever (o tratamento do conflito de versão no check-in será conferido no PR 47). Se um check-in ocorrer ao mesmo tempo, o `UPDATE` espera o bloqueio da linha do agendamento e reavalia `status = 'SCHEDULED'` (READ COMMITTED): se o check-in venceu, o snapshot fica como estava; se a edição venceu, o check-in congela o dado já atualizado. Teste de concorrência para os dois resultados.

**Obrigatoriedade de `petId`:**
- Hoje a API aceita `petId` opcional na reserva (compatibilidade). Depois que a tela exigir a escolha de um pet, `petId` passa a **obrigatório para novas reservas** (PR 49).
- A obrigatoriedade vale para **todos os pontos de entrada que criam agendamento**, não só `POST /api/appointments`. Hoje existe um único caminho (`BookingService.book`); a regra mora **nele** (camada de aplicação), não no controller, e qualquer caminho futuro (Remarcar, reserva sem conta) herda. Um teste por entrada existente e a regra de que **todo caminho novo que cria ou move agendamento** precisa passar por esse serviço e pelo bloqueio do pet (item 5).
- **Garantia no banco (PR 49):** `CHECK (pet_id IS NOT NULL OR created_at < '<data da migration>')`. Linhas antigas continuam sem pet e podem mudar de estado (o `CHECK` as dispensa pela data de criação, coluna `appointments.created_at` já existente); linhas novas sem pet são recusadas pelo banco, mesmo se uma rota esquecer a regra. A migration precisa de data fixa e será testada contra um banco com dados antigos antes do PR 49.
- Pet **arquivado** (`active = false`) não pode ser usado em nova reserva (**422 `PET_INACTIVE`**).
- Pet de outro cliente ou inexistente: **404 `PET_NOT_FOUND`**, mesma resposta (não revela que existe). A conferência de dono vem **antes** da de ativo, então `PET_INACTIVE` só aparece para o dono do pet.

### 3. Quem pode o quê
- **CUSTOMER:** lista, cria, altera, arquiva e **reativa** os próprios pets (`/api/customer/pets`). Limites: **20 pets ativos** e **100 no total** (ativos + arquivados, para não encher a tabela criando e arquivando em ciclo), ambos `409 PET_LIMIT_REACHED`. Não há exclusão física. A listagem devolve só os ativos por padrão (`includeArchived=true` mostra todos).
- **PROVIDER e ATTENDANT:** só **leem** o pet do agendamento em que operam, pela agenda e pela fila; nunca listam pets nem editam cadastro. Outros prestadores não veem.
- **ADMIN:** sem acesso a pets (como não tem a agenda).

### 4. O que cada tela vê (autorização na API, não na interface)
- O bloco opcional `pet` (`name`, `species`, `breed`, `size`, `notes`) vem **do snapshot do agendamento** e só existe nas respostas dos endpoints que **já autorizam** aquele agendamento: agenda do dia e fila (prestador dono ou atendente vinculado a ele), "Meus agendamentos" (o próprio cliente). A consulta que devolve o agendamento já filtra por prestador/cliente; `notes` não tem endpoint próprio, portanto não há como lê-lo fora dessa autorização. Teste: outro prestador, outro cliente e ADMIN **não recebem** `pet` nem `notes` em nenhuma resposta, nem por tentativa de adivinhar ids.
- **Minimização:** a agenda da semana (visão de várias linhas) mostra só `name`, `species` e `size`; `notes` e `breed` aparecem na agenda do dia e na fila (onde o atendimento acontece). "Meus agendamentos" mostra `name` e `species`.
- Arquivar não esconde o pet do histórico (o snapshot permanece).

### 5. Concorrência e integridade (protocolo de bloqueios)
Todas as operações que dependem do estado de um pet bloqueiam **a linha do pet** (`SELECT ... FROM pets WHERE id = ? AND customer_id = ? FOR UPDATE`, que já confere o dono) e só então decidem. Ordem de bloqueio, igual em todo o sistema: **cliente → pet → agendamento**. Quem não precisa de um nível pula esse nível, mas nunca volta atrás; isso impede impasse (deadlock).

1. **Reservar × arquivar (a corrida central).** A reserva bloqueia a linha do pet e **só depois** confere `active`. Se a reserva vencer, ela é confirmada e o arquivamento seguinte continua permitido; se o arquivamento vencer, a reserva enxerga `active = false` e falha com `PET_INACTIVE`. Ler `active` sem bloquear **não basta**: entre a leitura e a gravação o tutor pode arquivar, e a reserva entraria com um pet já arquivado. A transação compartilhada, sozinha, também não resolve (em READ COMMITTED a leitura não impede a escrita alheia); quem resolve é o bloqueio da mesma linha em ambos os lados. Validação e gravação do agendamento ocorrem na MESMA transação; a restrição de exclusão contra reserva dupla não muda.
2. **Limite de pets ativos (e total).** **Toda** operação que cria um pet ativo (criar, reativar) segue o mesmo protocolo na mesma transação: bloquear a linha do **cliente** (`FOR UPDATE`), contar ativos e total, inserir/reativar. Existe **um único método** de serviço para isso e nenhum outro caminho de gravação de pet (sem `INSERT` em outro lugar; teste de reflexão/estrutura confere que só ele escreve em `pets`). Cenário: duas criações simultâneas com 19 ativos terminam com 20, uma recebe `PET_LIMIT_REACHED`; o teste usa vários pedidos em paralelo e confere `COUNT(*) <= 20` no banco.
3. **Editar × reservar/check-in.** A edição bloqueia o pet, grava e atualiza snapshots dos agendamentos `SCHEDULED` (item 2). A reserva bloqueia o mesmo pet: serializam. Check-in e cancelamento bloqueiam só a linha do agendamento (não tocam o pet), então não formam ciclo com a edição.
4. **Arquivar com agendamento futuro:** **permitido** (o agendamento segue válido; só novas reservas são recusadas). A tela avisa.
5. **Remarcar (ADR futuro)** é "mover" um agendamento: deve manter `pet_id` e snapshot e respeitar a mesma ordem de bloqueios.

### 6. Dados pessoais
`notes` é texto livre do tutor: não entra em logs nem em respostas de erro (validação devolve o campo e o motivo, nunca o valor). Cliente desativado: os pets permanecem (histórico), mas ninguém novo os usa.

## Migrations (rascunho)
**V8 (PR 46), só `pets`:**
```sql
CREATE TABLE pets (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id uuid NOT NULL REFERENCES users (id),
  name varchar(80) NOT NULL, species varchar(3) NOT NULL, breed varchar(80), size varchar(6), notes varchar(500),
  active boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL, updated_at timestamptz NOT NULL,
  CONSTRAINT pets_name_ck CHECK (char_length(name) BETWEEN 1 AND 80 AND name = btrim(name)),
  CONSTRAINT pets_species_ck CHECK (species IN ('DOG','CAT')),
  CONSTRAINT pets_size_ck CHECK (size IS NULL OR size IN ('SMALL','MEDIUM','LARGE')),
  CONSTRAINT pets_breed_ck CHECK (breed IS NULL OR (char_length(breed) BETWEEN 1 AND 80 AND breed = btrim(breed))),
  CONSTRAINT pets_notes_ck CHECK (notes IS NULL OR (char_length(notes) BETWEEN 1 AND 500 AND notes = btrim(notes))),
  CONSTRAINT pets_id_customer_key UNIQUE (id, customer_id));
CREATE INDEX pets_customer_idx ON pets (customer_id, active);
```
**V9 (PR 47), vínculo e snapshot:** `ALTER TABLE appointments ADD COLUMN pet_id uuid, ADD COLUMN pet_name ..., pet_species, pet_breed, pet_size, pet_notes`; FK composta `(pet_id, customer_id)`; `CHECK` de consistência (`pet_id IS NULL` ⇔ `pet_name IS NULL`) e de formato. Sem preencher dados antigos.
**V10 (PR 49):** o `CHECK` de obrigatoriedade para linhas novas (item 2).
Os nomes e tipos exatos serão conferidos contra o esquema real (V1 a V7) no PR 46.

## Riscos a atacar na revisão
Integridade referencial (FK composta), autorização por dono, vazamento de `notes`, migração em banco com dados, corrida reservar × arquivar, corrida no limite de 20, edição × check-in, ordem de bloqueios, a exceção de snapshot em `SCHEDULED`, regressão dos 465 testes que reservam sem pet.
